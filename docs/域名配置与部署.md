# 域名配置与部署

本项目把公网入口分成三处协同配置：DNS 服务商把域名解析到服务器；服务器
环境文件配置 Caddy 证书和首次登录前的可靠入口；管理员登录后可在后台维护
当前访问域名及兼容别名。三处都需要保留。后台设置不读取或信任访问请求的
`Host` 头，也不能替代服务器上的 DNS、证书和反向代理配置。

## 三个环境变量

生产环境的 `.env` 中有三项必须描述同一个规范 HTTPS 入口：两项 URL 使用
同一个 origin，`CADDY_SITE` 使用该 origin 的主机名：

| 变量              | 作用                                             | 示例                          |
| ----------------- | ------------------------------------------------ | ----------------------------- |
| `CADDY_SITE`      | Caddy 申请证书并接收请求的主机名，不含协议       | `journal.example.com`         |
| `BETTER_AUTH_URL` | 登录、会话和始终保留的恢复入口                   | `https://journal.example.com` |
| `SITE_URL`        | 站点公开 URL，用于元数据、RSS、robots 与 sitemap | `https://journal.example.com` |

标准 Docker Compose 部署使用公网 TCP 80 和 443，因此生产地址只能是默认
443 端口的 HTTPS origin。不要填用户名、密码、路径、查询参数、片段或
通配符域名。

额外的登录地址统一在后台维护，不设置 `BETTER_AUTH_TRUSTED_ORIGINS`；应用会拒绝
这项旧环境变量，避免它留下后台无法撤销的另一份允许列表。浏览器认证请求始终
使用当前站点地址，不需要配置 `NEXT_PUBLIC_BETTER_AUTH_URL`。

`pnpm site:configure` 会在一次原子写入中只更新上述三项，保留其余环境变量、
注释、换行和引号，并将文件权限设为 `0600`。它不会搜索 `.env` 文件，必须
显式指定目标路径，也不会输出数据库或认证密钥：

```bash
pnpm site:configure --url https://journal.example.com --file .env
```

输入 `https://journal.example.com:443` 会规范化为同一个地址。标准 Compose
不支持通过该命令配置其他 HTTPS 端口；采用自行维护的反向代理或端口映射时，
需由该部署方案负责端口、TLS 和公开 origin 的一致性。

本地开发如确实需要 HTTP，只能显式使用 `--local` 和回环地址：

```bash
pnpm site:configure --local --url http://127.0.0.1:3000 --file .env.local
```

这只用于 `pnpm dev`。命令会把 `CADDY_SITE` 设为主机名，但不会改动 Caddy
监听端口，也不会把本地 HTTP 配置变成可部署的生产 Caddy 配置。运行
`pnpm site:configure --help` 可查看完整用法。

## 首次生产部署

首次部署时还没有管理员会话，因此必须先完成服务器配置；不能依赖后台的
“当前访问域名”设置来修复尚未登录时的域名不匹配。

1. 选择一个具体的完全限定域名，例如 `journal.example.com`。在 DNS 服务商
   创建指向服务器公网 IPv4 的 A 记录；仅当服务器也能从公网访问 IPv6 时再
   创建 AAAA 记录。等待解析生效后再继续。
2. 在服务器的防火墙、云安全组和上游网络中开放入站 TCP 80 与 443。Caddy
   需要从公网接收这两个端口的请求，才能自动申请和续期 HTTPS 证书。
3. 在项目目录复制环境模板并填好数据库、认证和 Server Action 密钥。数据库密码若
   含有 `@`、`:`、`/` 等 URL 保留字符，`DATABASE_URL` 中的密码部分必须做百分号
   编码；使用 URL-safe 随机密码可避免这一转换。Docker Engine 必须支持 BuildKit，
   因为 Compose 仅在构建期间以一次性密钥挂载传入
   `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`。不要把占位符或 `.env` 提交到版本库：

   ```bash
   cp .env.example .env
   chmod 600 .env
   # 生成并填写 POSTGRES_PASSWORD、DATABASE_URL、BETTER_AUTH_SECRET、
   # NEXT_SERVER_ACTIONS_ENCRYPTION_KEY 等值后，再设置公开地址：
   pnpm site:configure --url https://journal.example.com --file .env
   ```

   只安装了 Docker 的服务器不需要另外安装 Node 或 pnpm；可以直接编辑 `.env`
   中的三个域名变量，或借助一次性 Node 容器运行同一个配置脚本：

   ```bash
   docker run --rm --user "$(id -u):$(id -g)" \
     -v "$PWD:/work" -w /work node:24.21.0-bookworm-slim \
     node scripts/site-configure.mjs --url https://journal.example.com --file .env
   ```

4. 在 DNS 和端口都就绪后构建并启动服务：

   ```bash
   docker compose up --build -d
   docker compose ps
   docker compose logs --tail=100 migrate app caddy
   ```

   `migrate` 会在数据库健康后执行迁移，`app` 会等待它成功完成。Caddy 读取
   `CADDY_SITE` 后申请证书并代理到内部 app 服务。若证书申请失败，优先检查
   DNS 是否指向当前服务器，以及 80/443 是否可从公网访问。

5. 服务健康后创建首个管理员账号：

   ```bash
   docker compose --profile bootstrap run --rm bootstrap
   ```

   按提示输入管理员资料，或在短时间内通过 `ADMIN_EMAIL`、`ADMIN_NAME` 与
   `ADMIN_PASSWORD` 提供它们；不要把长期管理员密码保留在 `.env`。

6. 从同一个 HTTPS 地址打开 `https://journal.example.com/admin/login` 并完成首次登录。
   登录成功后，管理员可在后台填写当前访问域名和兼容别名。首次设置时通常无需
   添加别名，因为环境 URL 已是当前主域名。

## 管理员后台设置的边界

已登录管理员可维护站点的当前访问域名和迁移期间的兼容别名，供应用判断可信
来源和生成公开链接。它适合处理已经可访问站点的域名切换，不具备服务器管理
权限，因此不能：

- 创建、修改或等待 DNS 记录；
- 申请、安装或续期 TLS 证书；
- 修改 Caddyfile、Docker 端口映射或外部反向代理；
- 在未登录状态下绕过认证来源校验，或自动信任浏览器发送的 `Host` 头。

后台主地址为空时，应用继承 `.env` 的 `SITE_URL`；一旦后台保存了非空主地址，
该数据库值优先于环境值。环境中的 `BETTER_AUTH_URL` 仍然是可信的恢复入口，
因此即使后台主地址误填，也可从该环境 HTTPS 地址登录管理员后台并修正或清空
主地址。

后台域名误填时，使用服务器 `.env` 中的 `BETTER_AUTH_URL` 对应 HTTPS 地址
进入站点修正。若该入口自身存在 DNS、证书或代理故障，须先在服务器侧恢复
网络入口，再尝试登录。该环境入口应一直保留为可访问的恢复入口；不要因为
后台已经保存了新域名就删除、改成内网地址，或让它落后于实际可用的 HTTPS 入口。

## 更换生产域名

假设主域名从 `journal.example.com` 迁移到 `notes.example.com`。先让新域名的
DNS 指向同一台服务器，并确认公网 80/443 已经可达。后台兼容别名只影响应用的
来源授权；当前 Caddyfile 只为一个 `CADDY_SITE` 配置站点。把它改为新域名并
重新创建 Caddy 后，旧域名不会仅因后台别名而继续提供 TLS 或反向代理服务。
若迁移期必须保留旧入口，应先由运维人员在 Caddy 或上游反向代理中显式配置双
域名、相应证书以及旧域名的代理或重定向，再开始此处的应用配置迁移。

接着在服务器项目目录执行：

```bash
pnpm site:configure --url https://notes.example.com --file .env
docker compose up -d --force-recreate app caddy
docker compose ps
docker compose logs --tail=100 app caddy
curl -fsS https://notes.example.com/api/health
```

`site:configure` 同步更新新的 Caddy 主机名、认证 URL 和公开站点 URL。随后
必须重新创建 `app` 与 `caddy` 容器，使 Compose 在创建容器时重新读取 `.env`。
`docker compose restart app caddy` 只重启现有容器，不会重新载入环境变量，
因而不能完成域名变更。这个过程不会删除 PostgreSQL、媒体或 Caddy 数据卷；
新域名的证书会由 Caddy 按新的站点名申请。

容器重建和健康检查通过后，从新的 `.env` `BETTER_AUTH_URL` 打开
`https://notes.example.com/admin/login`。数据库中原有的非空后台主地址优先于
新的 `SITE_URL`，因此需要登录后把它改为 `https://notes.example.com`，或清空它
以继承新的 `SITE_URL`。确认新域名可以登录后，再根据实际迁移期限决定何时移除
旧 DNS、旧证书入口和后台兼容别名。在整个期间保留一个有效的环境 HTTPS 地址，
便可在后台配置出错或管理员无法从新地址登录时，重新进入后台修正设置。

## 多层代理下的图片上传

OpenResty、Nginx 或 CDN 可以在 Caddy 前终止 HTTPS，再通过内部 HTTP 转发。
此时应用看到的 `X-Forwarded-Proto` 可能是 `http`，与浏览器的 HTTPS 地址不同。
上传接口使用与登录相同的可信来源列表（环境中的 `BETTER_AUTH_URL`、后台主地址
及显式别名），不再用内部 `Host`、`X-Forwarded-Host` 或 `X-Forwarded-Proto`
拼接浏览器地址。无需为上传关闭来源校验或开放通配 CORS。

浏览器必须提供精确匹配的 `Origin`；有 `Sec-Fetch-Site` 时仅接受 `same-origin`。
上游代理应保留这两个浏览器请求头。后台删除兼容别名后，下一次上传即不再接受
该来源。登录状态、首次改密要求、文件格式与大小校验、私密媒体访问规则仍然生效。

上传失败的提示分别为：

- `UNAUTHORIZED`：会话不存在或账号已停用，先重新登录。
- `INVALID_ORIGIN`：当前地址不在站点配置内，或浏览器标记为跨来源请求；核对后台的
  主地址和兼容别名，以及代理是否改写了 `Origin` / `Sec-Fetch-Site`。
- `PASSWORD_CHANGE_REQUIRED`：账号确实处于首次改密状态，先完成密码修改。

从旧版升级此修复只需要更新应用镜像，没有数据库迁移。沿用原部署的环境文件和
Compose 附加配置；标准部署在对应分支执行：

```bash
git pull --ff-only
docker compose up -d --build --no-deps app
docker compose ps
```

保留原有密码、密钥和数据卷；更新后刷新后台再上传图片。
